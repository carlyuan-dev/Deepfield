# Deepfield Base.Usage 设计文档

版本：0.3 · 更新日期：2026-09-18  
状态：首版已实现并完成代码审查、自动验证与测试包构建，待用户真实调用验收。  
上位文档：[Base.overview 设计文档](base.overview.设计文档.md)。

## 1. 目标与非目标

### 1.1 目标

- 所有正式 LLM、Search 调用通过统一入口自动采集，上层无需手写计数。
- 覆盖 Chat、Capability、标题生成、公司识别、格式修正、配置诊断和后台连接检查等实际调用。
- 底层保留 Profile ID、调用时配置快照和来源；首版看板只按 LLM 的 Provider → 模型、Search 的 Provider 汇总，不提供 Profile 筛选或明细入口。
- 记录接口实际返回的用量，并明确缺失、失败、取消及记录异常的边界。
- 历史数据独立于对话、公司、报告和 Profile 的删除而保留。

### 1.2 非目标

- 不计算金额，不维护价格表，不判断免费额度剩余，不对接服务商账单。
- 不控制任务搜索上限、Token 预算、重试策略或是否开放联网工具。
- 不把 Search 调用次数直接称为计费次数或积分消耗。
- 不保存提示词、搜索词、回复正文、API Key、原始请求头或原始错误响应。
- 不承诺覆盖其他应用使用同一 Key 产生的用量。
- 不尝试从旧报告字数、历史消息或工具日志推算上线前的 Token 用量。

## 2. 统一记录口径

### 2.1 记录单位

一条记录对应一次由统一调用入口发起的 LLM 或 Search 尝试，而不是一次用户任务、一个报告或一条工具展示记录。

- Agent Loop 每次模型生成分别记录，最终收口也是独立生成。
- 业务重试、格式修正和可观测的底层重试分别产生新 `attemptId`，通过 `operationId` 关联。
- 同一尝试的流式片段、终态事件或跨进程重投不新增记录。
- 应用缓存命中、工具结果复用没有外部请求，不计入请求次数；模型服务的提示词缓存仍属于真实调用，记录其缓存 Token。
- 配置、参数、安全策略或预算在本地拦截的调用，不计入服务请求；原因由原有诊断/审计承担。
- “已发起请求”表示到达客户端传输边界，不保证服务商已经接收或计费。连接失败和超时仍保留尝试记录。
- 必须核查 SDK 隐藏重试：优先关闭隐藏重试，使用可记录的重试路径；无法逐次观测时必须标记尝试计数不完整，不能宣称全部物理请求已准确统计。

### 2.2 LLM 用量

记录输入、输出及可获得的缓存读取、缓存写入 Token。按协议适配器归一化，不能直接把不同 SDK 的同名字段相加。

- `inputTokens` 表示包含缓存部分的总输入；`cacheReadTokens`、`cacheWriteTokens` 是其中可确认的子集，不再加进总量。
- `outputTokens` 表示服务商报告的总输出，推理 Token 如已包含则不重复相加。第一版不单独展示推理 Token。
- `totalTokens` 优先从完整且归一化后的输入、输出求和；仅返回总量时可以单独保留总量，输入和输出仍未知。
- 缺失值用 `null`，不是 `0`。只有服务商明确报告或协议定义能确认的零才可记录为零。
- SDK 填充的默认零、历史消息占位 usage、客户端估算不视为服务商实测值。
- 用量状态为 `reported`（输入输出完整）、`partial`（仅部分指标可确认）、`unknown`（没有可确认指标）；它与请求成功/失败状态独立。
- 失败或取消也可能有用量；保留已获得的指标。没有最终 usage 时，不根据已显示的文字长度补算。
- 同一尝试的累计 usage 快照采用替换/补全语义，不逐块相加；终态用量不得被较早的片段覆盖。

### 2.3 Search 用量

- 分别统计已发起次数、成功次数、失败次数、取消次数和结果未确认次数。
- 合法的空结果属于成功；HTTP 200 但业务错误属于失败。
- 返回条数可以记录为辅助指标，不代表搜索次数，也不代表收费单位。
- `web_fetch` 不混入 Search 请求；第一版只统计已接入 Search Provider 的实际搜索调用。

### 2.4 计数的诚实边界

看板统计的是本应用可观测用量，不是服务商权威账单。即使所有请求成功，若服务商没有提供 usage，Token 仍可能未知。看板同时展示已知用量和未知/部分用量请求数，不能只给一个看似完整的总数。

## 3. 通用数据契约

字段命名为设计建议，实现可调整命名，但不得改变统计语义。

| 字段组 | 核心字段 | 约束 |
| --- | --- | --- |
| 唯一标识 | `attemptId`、`operationId` | 每次实际尝试唯一；同一逻辑操作可有多次尝试 |
| 来源上下文 | `sourceId`、`taskId?`、`stageId?`、`parentTaskId?` | 有长度上限的普通标识；禁止自由正文；缺省来源为 `unclassified` |
| 配置快照 | `serviceKind`、`profileId?`、`profileName`、`providerId`、`modelId?`、`configRevisionId` | 保存调用当时的非敏感信息；不保存 Key 或可推导 Key 的指纹 |
| 草稿归属 | `draftSessionId?` | 未保存诊断单独分组，不假装已有 Profile；不自动合并到之后保存的 Profile |
| 生命周期 | `startedAt`、`finishedAt?`、`outcome`、`durationMs?`、`revision` | 状态：running / succeeded / failed / cancelled / interrupted；时间统一 UTC |
| LLM 指标 | `inputTokens?`、`outputTokens?`、`cacheReadTokens?`、`cacheWriteTokens?`、`totalTokens?`、`usageStatus` | 缺失为 null；非负安全整数；缓存不可重复计入 |
| Search 指标 | `resultCount?` | 每条有效搜索尝试计一次，条数另存 |
| 完整性 | `attemptCountStatus`、`errorCode?` | 记录可观测性状态和安全错误码，不存原始异常正文 |

`serviceKind` 第一版仅支持 `llm`、`search`，不提前建设任意指标插件系统。未来增加资源类型时扩展契约及该资源适配器，不修改已接入的业务模块。

### 3.1 Profile、Key 与服务商的区别

- Profile 是产品内配置标识，不是计费账户。同一 Key 可用于多个 Profile，同一服务商也可有多个账户。
- 底层以稳定 `profileId` 保留归属。界面中 LLM 按 `providerId` → `modelId`、Search 按 `providerId` 汇总；同组多个 Profile 相加，每个 attempt 仍只计一次。
- Profile 重命名、换模型、换服务商或换 Key 时形成新的非敏感配置修订标识；历史调用快照不改写。
- 不识别或展示“每个 Key 消耗”，也不自动合并使用同一个 Key 的 Profile。
- 已删除 Profile 的 ID、历史名称和快照继续保留。看板按调用时 Provider／模型归组，不套用 Profile 当前值，也不为历史 Profile 增加界面入口。
- 原始 Base 数据不包含“公司调研”“标题生成”等封闭业务枚举；来源 ID 和显示名称由上层目录解释，新业务无需修改 Base。

## 4. 采集与存储接入

### 4.1 采集职责

统一调用入口持有注入的 `UsageRecorder`。业务只提供上下文，调用入口负责生成尝试标识、捕获开始/结束、归一化指标并上报。LLM SDK 和各 Search 协议的差异由采集适配层处理，Usage 不导入第三方模型 SDK 类型。

```text
Chat / Capability / 应用服务
  → 统一 LLM / Search 调用入口（含采集适配）
      → 外部服务
      → UsageRecorder（通用开始/终态记录）
          → 主进程 UsageService
              → UsageRepository 端口
                  → SQLite 适配器

Settings → 应用 IPC 查询接口 → UsageQueryService → 同一账本
```

图中是运行数据流。Worker 到主进程的传输适配、IPC 和 SQLite 驱动不属于 Base 核心；由现有应用初始化代码连接具体实现，暂不单列“应用装配与平台适配”架构层级。Base 仅定义通用记录、查询和存储端口，不调用上层业务。

### 4.2 当前代码接入点

| 现有路径 | 接入要求 |
| --- | --- |
| `apps/desktop/src/shared/model-gateway.ts` 直接生成 | 在丢弃 SDK usage 前采集，覆盖标题、识别、结构化及其修正重试 |
| `apps/desktop/src/worker/pi-chat-agent.ts` 流式生成 | 收拢模型 stream 入口并采集每轮终态，包括工具阶段和最终收口；不能只观察最终回答 |
| `packages/retrieval/src/providers/provider-registry.ts` 及 Provider 公共调用边界 | 注入统一采集包装，保持 provider 协议实现不感知业务来源 |
| `apps/desktop/src/main/configuration-service.ts` | 诊断使用同一采集入口，覆盖已保存 Profile 和未保存草稿 |
| 主进程 / Worker 装配入口 | 注入相同契约的记录器及明确来源，主进程统一持久化 |

不能仅在 `web_search` 展示层计数，也不能仅在 `completeText` 计数。当前这两种做法都会漏掉其他调用路径。实施时盘点 SDK、HTTP 客户端及工厂构造点，限制正式业务绕过统一入口。

### 4.3 公共接口职责

- `UsageRecorder.recordStart(start)`：记录已发起的尝试。
- `UsageRecorder.recordFinish(finish)`：记录成功、失败或取消及已知用量；同一终态重复传递必须幂等。
- `UsageRepository`：按尝试 ID 和修订号写入与查询，不包含业务仓储方法。
- `UsageQueryService.getSummary(query)`：总览与完整性摘要。
- `UsageQueryService.getDailySeries(query)`：日趋势。
- `UsageQueryService.getBreakdown(query)`：首版提供 LLM 的 Provider → 模型、Search 的 Provider 聚合。Profile 和来源维度保留在记录中，暂不要求实现其聚合查询。
- 按 Profile 检索与 `listAttempts(query)` 分页明细留作后续诊断扩展；首版不增加对应页面、筛选器或 IPC 明细接口。
- `UsageQueryService.getHealth()`：采集启用时间、待落盘/异常状态与恢复信息。

上层不调用自增计数接口，也不直接写 Usage 表。统计由账本推导，不维护一份容易漂移的独立总数。

## 5. 持久化与异常恢复

第一版复用本地 SQLite，通过现有迁移机制新增独立用量表；主进程为唯一写入者。不新建服务、不引入消息队列，也不跨进程共享数据库写连接。

- 主表以 `attemptId` 为唯一键，存放快照、状态和归一化指标；按时间、Profile、服务类型建立必要索引。
- 开始与终态允许乱序：终态携带完整公共快照，可以独立 upsert；迟到的开始不能覆盖终态。
- Worker 使用有确认的记录传输，未确认消息在有界队列内重投，同一记录重投不重复计数。按 ID 与修订号处理重复和过时写入。
- 单次任务终止不丢弃正在提交的用量消息；正常退出执行有时间上限的 flush。
- 应用启动时把上次遗留 running 记录标记为 interrupted，保留已知指标，未获得的用量仍为未知。不得自动重发模型/搜索业务请求来“修复账本”。
- 写入异常不导致 Chat 或调研失败；有界重试，超出界限产生统计健康告警。恢复后重新提交仍在队列的记录。
- 内存队列无法保证强制退出后的零丢失：不宣称 exactly-once 全链路投递或崩溃场景绝对完整。启动发现异常关闭、遗留记录或投递失败时，在看板提示相应完整性风险；实现应保留正常关闭标识以识别异常退出。
- 不因删除对话、公司、报告或 Profile 级联删除用量。第一版不自动清理账本、不提供未经确认的清空按钮。

记录器在数据进入队列前做白名单校验；诊断日志仅含尝试 ID、安全错误码和失败阶段。不能把整个 runtime snapshot 序列化入账本，因为其中包含 Key。

## 6. 查询与看板

### 6.1 查询规则

- 默认本月，支持今天、近 7 天、近 30 天及自定义起止日期；采用当前界面时区。自定义包含起止两天，最长 366 个本地自然日，非法区间明确报错而不截断。
- 存储 UTC，按指定时区生成自然日边界；查询采用 `[from, to)`，统一按尝试开始时间归属日期，跨日完成不产生第二条记录。
- 默认包含全部来源，包括诊断、连接检查和未保存草稿调用。界面提供时间范围和 LLM／Search 切换；LLM 趋势另按 Provider＋模型选择，顶部总览和下方 Provider 汇总保持全部模型。没有 Profile 或来源筛选器。
- 汇总返回已知指标及未知/部分用量数量。没有完整数据时使用“已记录 Token”，不显示成精确总消耗。
- `running`、`interrupted` 与明确失败分开；结果未知不能自动算成功或失败。
- 历史开始时间为本功能启用时间；上线前显示“未统计”，而不是零消耗。

### 6.2 Settings 呈现

设置入口命名“用量信息”，不出现人民币金额或账户余额。

1. 顶部概览：已记录输入/输出 Token、Search 请求次数、统计完整性提示。
2. 中部趋势：LLM 显示 API 请求次数折线图和 Tokens 堆叠柱状图两张固定高度图卡；Search 使用请求次数普通柱状图。图框不随日期数量变化，窄窗口下两张卡上下排列，桶不换行。今天及自定义单日按小时，多日按天；未来时段不冒充已统计的零。整列鼠标悬停或键盘聚焦显示对应时段详情。
3. 下部横向贡献排行：LLM 按 Provider 展示，各 Provider 下展示模型汇总；Search 直接展示各 Provider。可显示同组成功/失败/取消等汇总数字，不提供 Profile 或逐次调用明细入口。
4. 固定说明：“仅统计本应用可观测用量，不代表服务商账单或剩余额度。”
5. 未知用量与统计写入异常明确提示；未保存诊断、已删除 Profile 的调用照常纳入对应 Provider／模型汇总，不额外暴露配置维度。不显示常驻“统计启用时间”文字，但保留底层时间及覆盖范围判断。Search 图表与 Provider 贡献条使用一致绿色系。

Tokens 按每次调用拆分命中缓存输入、未命中缓存输入、输出，再汇总。已知总输入且已知缓存命中时，未命中为两者差值；缓存写入已在未命中输入中，不重复叠加。缺失缓存信息时，已知但无法拆分的输入使用灰色段；未知值不补零，不从两份可能不完整的汇总值相减。现有账本字段足够，拆分属于查询投影，不回写或迁移历史数据。

第一版以进入页面、切换筛选时刷新为基础；页面可见且有活动时低频刷新，不在每个 Token 到达时刷新整张图。图表是查询投影，不能成为记录是否发生的前提。

## 7. 最小验收范围

| 场景 | 必须确认 |
| --- | --- |
| 一次非联网 Chat | 模型调用有记录；标题生成若发生则单独归类 |
| 联网 Chat 多轮 Loop | 各轮模型、真实搜索、最终收口分别记录；工具结果复用不重复计数 |
| 两轮调研与格式修正 | 一轮、二轮、修正均能采集，上层不手工累加 |
| Settings 未保存诊断 | 独立草稿归属，既不漏记也不改变当前配置 |
| 搜索失败/空结果/本地拦截 | 正确区分失败、成功空结果和未发出请求 |
| 缓存与缺失 usage | 缓存无重复计量，SDK 默认零不冒充实际零，未知值可见 |
| 取消/重复投递/乱序 | 同尝试只计一次，已有用量不丢，旧事件不能覆盖终态 |
| Profile 修改/删除、业务记录删除 | 历史归属快照和账本保留，按调用时 Provider／模型归组 |
| 看板简化 | LLM 按 Provider → 模型、Search 按 Provider 汇总；无 Profile 筛选或明细入口；多 Profile 不重复计数 |
| Worker 异常、存储失败 | 业务不因统计失败而失败；看板明确不完整状态 |
| 跨日/月切换 | 日期边界一致，不漏计或重复计入相邻区间 |
| 新增最小测试 Capability | 只使用统一调用入口和来源上下文即可入账，不修改 Usage |
| 依赖检查 | Base 反向导入上层时检查失败 |

使用小范围协议 fixture、调用链集成和 UI 测试证明关键语义；不以消耗大量真实额度换取测试覆盖。真实 Key 的最终可用性由用户手测验证。

## 8. 实施顺序与动态维护

1. 明确归一化契约，建立 Base 公开入口与依赖边界检查。
2. 建设 Usage 记录/查询服务、SQLite 适配与跨进程传输。
3. 收拢全部 LLM、Search 调用入口并采集；验证重试、取消、未知值与防重复。
4. 接入 Settings 用量看板。
5. 验收后再盘点其他共用能力，逐个决定是否进入 Base。

本文维护 Usage 专属契约、统计口径和看板设计。Base 的总体边界与能力域目录见 [Base.overview 设计文档](base.overview.设计文档.md)。其他能力域独立成文，不堆入本文或总览；未实现能力不得描述为已具备。

## 9. 首版落地边界

- 已接入桌面端 Chat 各轮、标题、公司识别与补全、两轮调研及修正、配置诊断与连接检查；独立开发诊断 CLI 保持隔离，不写用户账本。
- Base 服务通过仓储端口显式注入；桌面适配器在每个进程绑定一个记录器，未来新功能应复用 `PiModelGateway` 与 `createMeteredSearchProvider`，不绕过统一入口自行构造 SDK 或未采集的 Search Provider。
- SQLite 为 migration 20。主进程统一写入，单进程投递队列上限 256、每条最多尝试 3 次；正常退出有界等待，未确认 Worker 落盘会持久化完整性告警，不推算丢失条数。
- 原始流式 usage 在 SDK 映射前采集，保留缺失值；观察器单行上限 65,536 字符，过大或无法解析的事件不影响原始响应，但对应指标可能未知。Anthropic 兼容端若缺少缓存子项，不能确认的总输入保持未知。
- Settings 的统计周期、趋势交互与模型选择按第 6 节演进；首次启用前标为未统计，无历史用量回填。
- 自动测试使用协议 fixture 和内存 SQLite；服务商真实用量返回情况与用户最终交互仍由手测确认，不将本地统计视为账单。
# 2026-09-22 统计投影、提示与恢复规则（覆盖旧规则）

以下规则覆盖本文中与之冲突的旧统计与健康描述：

- LLM 看板的概览、日序列、趋势、Provider、模型汇总和自动模型选项使用同一投影。排除 `running`，并排除失败、取消或中断且五项 Token 指标全部为 `null` 的终态记录；成功但未知用量仍计请求数，任一已知指标（明确的 `0` 也算）保留。Search 仍按实际发起次数统计。
- 原始账本与提示投影独立。删除只适用于终态异常且所有 Token 指标为空的版本快照；成功未知、部分用量和尝试数不完整只做持久确认，不删除记录，也不改变任何统计。每条保留记录的确认随记录生命周期保留；新记录不会被旧确认覆盖。
- 运行中的 LLM 不进入任何数字或图表，但 `inFlightRequests` 单独驱动看板轮询。Search 的运行数仍按原口径呈现并驱动轮询。
- 当前故障与历史计数分离。只有当前存储/传输失败显示红色；累计失败次数本身不构成当前故障。超过 3 秒的正常待写入仅显示灰色同步状态。不可恢复的丢弃/中断是可持久确认的黄色历史缺口，确认不清零账本计数；计数增长会产生新提示。
- 投递失败记录在内存中按 `attemptId` 合并新修订并受容量限制。显式“修复”先做回滚式本地存储读写探测，再幂等重投保留事件；它不重发业务请求、不调用 Provider、不初始化仓库、不关闭/重启 Worker，也不使用关闭队列的 `flush`。旧修订不能覆盖新修订；退出时仍未恢复的记录转为真实历史缺口。
- 红色当前故障可收起为单行状态，但始终保留修复入口；实际恢复后自动消失。界面只显示安全的人类可读说明，不暴露底层异常文本。
