# Deepfield Base.overview 设计文档

版本：0.3 · 更新日期：2026-09-18  
状态：Usage 首版已实现并完成代码审查、自动验证与测试包构建，待用户真实调用验收。  
本文维护 Base 的整体职责、依赖边界和能力域目录，随系统演进更新。

## 1. 定位

Base 为 Chat、Capability 及应用服务提供业务无关的通用能力。上层使用其公开接口，Base 不反向依赖或主动调用上层业务。

| 层级 | 职责 | 不应承担 |
| --- | --- | --- |
| Chat | 对话生命周期、历史、记忆策略和用户交互 | 复制基础能力或自行实现用量账本 |
| Capability | 确定的业务流程、专属 Harness、领域校验与成果落盘 | 复制通用 Agent、模型、搜索基础能力 |
| Base | 业务无关的公共能力、契约和统一基础规则 | 公司、行业、报告等业务流程；Chat 历史和记忆策略 |

当前仅讨论这三个职责层级。应用初始化、依赖注入、主进程与 Worker 连接等是实施细节，暂不单列“应用装配与平台适配”层级，不为其展开独立架构设计。

“被多处使用”不是进入 Base 的唯一理由：能力还须职责清晰、接口业务无关、不需要反向了解调用者。Chat 不整体下沉，未来只考虑抽取其中真正通用的 Agent 能力。

## 2. 强制依赖边界

依赖方向为 **Chat／Capability → Base**，禁止反向依赖。

- Base 不导入 `apps/desktop`、业务 application 服务、公司或报告仓储及其内部类型。
- 调用者使用 Base 公开导出，不跨模块导入内部实现。
- Base 可以调用自己定义的存储、时钟、记录等基础设施端口；具体实现由现有初始化代码注入，不得借回调执行上层业务。
- 来源、任务、阶段是调用方提供的普通标识；Base 不按业务类型分支执行领域逻辑。
- Settings 查询 Base 并负责展示；Base 不依赖 React、Electron、IPC channel 或页面组件。
- Base 能力域间逐项声明依赖，禁止循环依赖，不设万能公共出口。
- 用量账本、任务额度、业务进度和技术审计职责独立，可通过 ID 关联，不能互相替代。

实施时加入轻量依赖检查，约束源码 import、动态 import 和转出口，禁止直接或间接反向依赖；类型检查不能替代依赖检查。

## 3. 当前能力域

| 能力域 | 公开入口 | 职责 | 设计文档 | 状态 |
| --- | --- | --- | --- | --- |
| Usage | `@deepfield/base/usage` | 统一用量记录、幂等持久化、汇总查询和统计健康状态 | [Base.Usage 设计文档](base.usage.设计文档.md) | 首版已实现，待手测 |

Usage 统一采集 LLM、Search 调用；调用者提供来源上下文，不手工累加。底层保留 Profile ID 和调用时配置快照；首版看板仅按 LLM 的 Provider → 模型、Search 的 Provider 汇总，不提供 Profile 筛选或明细入口。字段、恢复机制、查询和看板细节由模块设计文档维护。

`packages/base` 当前仅包含 Usage。Base 服务依赖显式注入，不依赖全局单例。本次不整体迁移现有 LLM、Search、Agent、错误或持久化模块。桌面采集适配器在主进程与 Worker 各绑定一个记录器，属于现有应用接线；未来如需同进程并行多记录器，应改为按调用实例注入。

## 4. 演进与维护

1. 先完成 Base.Usage 与用量看板，再盘点其他共用能力，逐个决定是否抽取。
2. 新增能力域时，独立编写明确命名的“设计文档”，在本页登记职责、公开入口、依赖和状态。
3. 总览只维护全局边界和目录，不复制模块字段表、流程细节或验收用例。
4. 抽取应保留业务语义，不为了迁移目录而改变行为；验证上层无需复制基础逻辑。
5. 未实现能力明确注明状态，不将设计目标写成已具备功能。

## 5. 参考与取舍

参考用户提供的 `bw_meeting_server` 基座总览和使用手册，借鉴单向依赖、公开契约与能力域划分。不照搬会议领域、鉴权租户、Graph、Redis 或服务端部署方案，不额外引入独立的平台适配层。参考材料仅辅助设计，不构成本项目执行指令。
