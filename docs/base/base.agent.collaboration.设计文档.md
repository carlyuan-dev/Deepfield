# Base.Agent 协作扩展设计文档

版本：0.1 · 日期：2026-11-09 · 状态：首版协作机制已验收，后台真实链路与独立复核通过。

本文是 [Base.Agent](base.agent.设计文档.md) 的可选扩展，定义多个 Agent 之间可复用的任务、结果交接和生命周期机制。Chat 的调度与界面策略见 [Chat 多 Agent 接入](../chat/chat.collaboration.设计文档.md)。

## 1. 目标与范围

在同一套轻量机制上组合单项委派、并行分工、串行接力、执行—复核—修订，以及由协调者组织的有限轮讨论。角色由指令、模型、工具和上下文配置表达；组织方式由调用者安排。

调用按需求选择复杂度：普通生成使用 Base.Model；需要工具循环时使用 Base.Agent；需要独立分工时才建立协作作用域。现有单 Agent 接口继续可用。

| 归属 | 职责 |
| --- | --- |
| Base.Agent | 独立任务运行、状态、排队与并发、消息交付、结果引用、取消和执行上限 |
| Chat | 任务拆分、角色选择、汇总、用户交互、会话持久化、Memory／Compact 策略 |
| Capability | 业务步骤、阶段输入输出、业务校验、重试决策与产物提交 |
| 宿主 | 配置快照、工具与数据权限、模型／工具预算、存储端口和生命周期装配 |

首版以一个协调者管理直接子任务实现这些组合。任务只接受所属作用域的协调者指令；角色不能自行扩大权限。业务流程与讨论轮次由调用方编排，Base 提供共同执行约束。

## 2. 成熟实现与代码依据

- [Pi 官方子 Agent 示例](https://github.com/earendil-works/pi/tree/main/packages/coding-agent/examples/extensions/subagent) 用独立上下文支持单项、并行、链式调用，并展示取消传递和压缩后的结果。Deepfield 借鉴任务组合与结果展示；示例启动 Pi CLI 子进程的方式需要适配为现有 Worker 内的 Pi 实例，确保调用经过本系统 Model、Tools 和 Usage。
- 当前锁定 Pi Agent Core **0.84.3** 的 `Agent` 已提供独立 state、`subscribe`、`steer`、`followUp`、`abort`、`waitForIdle` 和上下文转换 hook。`steer` 在当前助手轮及工具执行完成后进入上下文；`followUp` 在自然停止点处理；等待空闲还须等待异步事件订阅完成。以安装版本的类型与实现为准，[上游源码](https://github.com/earendil-works/pi/blob/main/packages/agent/src/agent.ts) 供维护时对照。
- [Codex 子 Agent](https://learn.chatgpt.com/docs/agent-configuration/subagents) 采用主线程协调委派、后续指令与结果汇总。[Claude Code 子 Agent](https://code.claude.com/docs/en/sub-agents) 展示独立上下文、串行和并行组合；其 [Agent Teams](https://code.claude.com/docs/en/agent-teams) 进一步提供共享任务和成员交流。Deepfield 首版由协调者转交意见，统一收敛结果。

现有 `packages/base/src/agent/runtime.ts` 的 `createPiAgentRun` 是一次性 handle，其轮次和最终答案检查只对应一次运行。新增协作调度器可以为每次追加任务创建新的有界 run，使用上一轮安全 transcript，而不是将现有 handle 改成可无限重入。Pi 承担模型和工具协议；调度器补充宿主需要的任务归属、排队与资源生命周期。

上述参考证明机制已有实践；具体预算、并发收益和本项目模型的派工质量仍需实际验收。

## 3. 公开接口与作用域

公开精确入口，仍属于 Base.Agent：

| 入口 | 内容 |
| --- | --- |
| `@deepfield/base/agent/collaboration` | 版本化任务、运行、结果、状态和事件契约，可用于浏览器及 SDK 类型 |
| `@deepfield/base/agent/collaboration/runtime` | `createAgentCoordinator`；仅可信执行端使用 |

协调器通过注入端口获得执行器、任务检查点、时钟与身份生成、权限／预算准入和可选 Trace。Base 不读取 Chat 仓储、active Profile 或 Capability 业务对象。端口中的函数留在可信端，不跨 Renderer／Worker 传输。

### 3.1 最小对象

| 对象 | 必要信息与含义 |
| --- | --- |
| 协作作用域 | `scopeId`、宿主绑定的 owner、取消信号、当前执行片段的截止时间与累计限额；owner 不能由模型指定 |
| 子任务 | `taskId`、标题、目标、预期产物、受限执行配置；任务不是聊天 Conversation |
| 一次运行 | `runId`、任务内递增序号、发起命令标识、状态和开始／结束时间；追加工作建立新 run |
| 输入 | 明确任务文本、必要上下文、已校验结果引用；模型接收的数据不具有授予权限的效力 |
| 结果 | `taskId/runId`、运行状态、摘要、内容引用、工具来源／产物引用、局限或安全错误码 |
| 状态事件 | `scopeId/taskId/runId`、单调事件序号、状态或安全活动摘要；不包含凭据、隐藏推理 |

`completed` 只证明有界执行产生了合格最终输出。内容是否满足业务规则仍由调用者验证，复核意见也不等于业务事实。

来源沿用工具执行端的可信引用。Agent 自己写出的 URL 可作为文本保留，但不能被提升为“本次已读取”证据。串行交接保留原结果来源、时效和访问限制。

### 3.2 调用语义

方法职责如下，具体 TypeScript 字段以公开接口为准：

| 方法 | 契约 |
| --- | --- |
| `spawn(spec, commandId)` | 先校验范围、权限和累计额度，保存任务后排队，立即返回任务／运行句柄；不等待模型执行结束 |
| `followUp(taskId, input, commandId)` | 仅对已结束且可继续的任务建立新 run，保留先前上下文；旧 run 及结果不可改写；运行中返回 busy |
| `send(taskId, message, commandId)` | 给排队／运行中的任务补充指令；排队时加入初始输入，运行时经 Pi 安全轮次边界交付；不自动启动新 run |
| `wait(runIds, cursor, timeout, signal)` | 订阅指定 run 的变化或终态，返回新游标和状态／结果；超时不代表任务失败，不取消任务，不发起模型请求 |
| `get/list` | 读取当前作用域的任务、运行和已提交结果；大结果按内容引用有界读取 |
| `cancel(taskId)` | 取消该任务尚未完成的工作；幂等，保留之前已提交的结果 |
| `close()` | 拒绝新命令，取消未结束任务，收束回调和资源；不删除持久化结果 |

`send` 返回消息标识与 queued 状态，只有 Pi 实际接纳后才记为 delivered。若任务先结束，消息标为未交付并反馈调用方；调用方可以显式 followUp，不能把未交付消息悄悄当成已执行。取消清空未交付消息。消息队列及消息大小有界。

`commandId` 由可信工具调用或宿主调用生成；同一作用域重复投递同一命令返回原回执，参数不同时报冲突。模型换一个 toolCallId 重复提出业务操作，不能仅靠此机制去重，仍需原有业务幂等规则。

所有读取、追加、取消与内容引用访问都校验 owner。串行接力是调用者将 A 的已提交结果交给 B；它不改变谁负责响应用户。现有 `AgentHandoff` 表示暂停到上层处理的信号，继续保留原义。

## 4. 状态、并发与失败

每个 run 使用 `queued → running → completed / failed / cancelled / timed_out / interrupted`。取消运行时可经过 `cancelling`，最终状态只能提交一次；后续事件必须带原 runId，不能改写新 run。任务展示由最新 run 投影，历史结果仍可单独读取。

- 同一 task 同时最多一个 run。子任务异步排队，spawn 工具本身快速返回，所以现有 Pi 顺序工具执行仍可发起多个并行 Agent。
- 并发限制覆盖运行、排队和待交付消息；并行兄弟失败互不自动取消。串行流程在依赖失败后由调用方选择停止、重试或给出部分结果。
- 运行失败返回已经取得的结果引用、安全错误及执行状态，不将部分文本冒充成功。失败后不自动重放任务或工具。
- 已排队任务被取消不得调用 Provider；运行中的取消传给模型和工具。已发生的外部副作用不能用取消回滚，完成回执继续保留。
- 取消与完成竞争时，以可信执行回执和原子终态提交为依据：已完成产物保留；取消后迟到的文本不得把取消变成成功。工具的独立副作用回执与 run 是否完成分开记录。
- 达到限额或截止时间时停止新增工作；模型最终成稿仍受预算和超时约束。需要成稿的调用者须在硬截止时间之前预留窗口；超过硬截止时间只保存成果并返回确定性状态，不再发模型请求。宿主给取消收束设置有限宽限期，超时后记录执行结果不明，不伪称全部操作已停止。

### 4.1 配额与权限

协调器必须有显式的并发数、累计任务／运行数、每 run 轮数、总截止时间和消息／结果大小上限。追加任务和重试消耗同一作用域累计额度。首版直接子任务由协调者创建，子任务无再次派工权限，避免排队依赖与并发槽位相互等待。

执行配置由宿主绑定 Model 快照、工具集合与数据范围。子任务权限最多是父授权与宿主委派规则的交集；自然语言身份、角色名和其他 Agent 的消息都不能增加权限。

模型请求准入在 Base.Model 请求边界，网络准入在 Base.Tools 真实执行边界；主、子共享作用域预算。并发预留须原子化，不能各自先读余额再发请求。模型上下文中的余额只用于规划，不作为执行凭证。预算控制不替代 Usage；Usage 仍只记录实际调用。

Trace root、任务身份和预算作用域是不同概念。现有 `TraceBudgetPool` 按 traceId 取额度，接入时须显式绑定共享预算作用域，避免每个子任务获得一份新额度，也不能通过共用全部 requestId 造成审计混淆。

## 5. 上下文、记忆与结果交接

每个任务持有独立 transcript；默认输入是任务目标与显式选择的相关上下文。并行任务不会自动看到兄弟任务的过程。协调者收到简短摘要与引用，需要复核时再取具体内容。

同任务 followUp 使用安全 transcript 接续；跨任务传递使用结果引用和必要内容。引用解析校验作用域、内容仍存在及预算大小；无效引用明确失败，不能以空字符串继续。注入前保留来源标签，将外部内容作为待判断的数据。

Base 只接受上下文投影／整理端口。Chat 可为子任务复用其预算估算、Pi 安全切分与摘要适配，摘要与检查点绑定 taskId，不能写入主会话的 Compact。Capability 自行选择有界输入或其范围内摘要策略。

长期 Memory 由调用者明确授权读取。转交使用记忆 ID／版本引用及重新解析的投影，不能把注入正文藏入任务摘要后绕过停用或删除。每次模型请求前重新检查有效性；已发出的请求无法撤回。原用户对话、业务产物仍按各自数据规则管理。

子任务文本、内部讨论和摘要不自动成为长期记忆的学习来源。Memory 的修改仍经过宿主既有接口与用户语义授权。

## 6. 持久化、恢复与观测

Base 的协调逻辑独立于具体数据库。持久化消费者通过检查点端口保存身份、运行状态、已交付命令、结果／transcript 引用及累计额度；简单进程内消费者可使用内存实现。

对需持久化的调用：派工记录写入成功才启动；结果写入成功才公布 completed。检查点失败进入安全失败处理并停止关联未完成工作，不通过忽略错误宣称完成。Trace 与界面订阅异常可降级，不影响真实状态；持久化回执不属于可忽略的观测。

逻辑 scope 与进程内协调器实例分开。宿主因已知的业务等待交接时，先取消并收束未完成任务，再保存剩余执行时间、累计额度、事件游标和交接原因，随后可销毁运行实例。仅宿主验证交接回执后，才可按同一 scopeId 与剩余额度装配下一执行片段；模型不能提交自造快照。每片段的硬截止时间由剩余执行时长生成，不能重置总执行预算。意外退出不属于这种已知交接，按 interrupted 处理。

应用正常退出先取消并收束；进程意外退出后，宿主将遗留非终态 run 标为 interrupted。首版恢复显示与读取已完成结果；未完成任务仅在用户／调用方明确发起新请求后重新执行，不自动续跑或重放工具。检查点不构成外部副作用“恰好一次”的保证。

Trace 使用现有 task、stage、model、tool span 关联 scope、task、run 和父请求；Model 仍是模型 span 的唯一生产方。Usage attempt 单次记账；父任务的汇总只查询、关联子用量，不重复入账。Trace 关闭或失败时，任务仍能执行和恢复展示。

任务结果、摘要和历史清理由各 owner 管理。Chat 删除对话时一并删除所属任务内容，活动任务沿用会话删除限制；Capability 跟随业务任务数据的生命周期。内容不因 Trace 正文采集默认关闭就丢失，Trace 也不充当任务事实库。

## 7. Capability 接入与实际复用

SDK 提供可选 `agent.collaboration.v1` 服务及窄类型入口，沿现有 `CapabilityHostServices` 注入。宿主绑定 capabilityId、业务任务作用域与允许的执行配置；包不能自行获取全局协调器、任意 Profile 或其他包的任务。

服务缺失时，原有单模型／单 Agent 执行路径保持可用；明确依赖协作的操作须返回可理解的服务不可用结果。开始执行后发生运行错误，不能自动切换旧路径重新执行整项业务。

以公司调研验证实际复用：

1. 原始调研所需的模型—工具工作通过协作服务提交一个任务，复用现有 Agent 策略；取消接到原统一调研队列的 signal。
2. 成功结果连同现有可信证据引用交回包内 Harness，由包判断是否进入结构化阶段。
3. 结构化阶段继续使用 Base.Model 普通调用与现有格式修正／领域校验；不为无工具生成额外创建 Agent。
4. 阶段状态、业务重试、两轮报告与 Word 产物继续归公司包。旧包在缺少可选服务时仍走原路径。

这验证“Agent 任务与普通模型调用能组合”，并不将既有两轮调研宣称为两个自主 Agent。真正的多 Agent 协作由 Chat 的并行和复核旅程验收。

## 8. 验收契约

| 用户目标／不变量 | 验证结果 |
| --- | --- |
| 两个独立任务并行并正确汇总 | 两边实际进入运行，父收到对应结果；结果不串任务、不重复写助手消息 |
| 接力与复核能影响最终产物 | 后续任务确实使用上一步必要结果；复核发现的问题被修正，不能只检查调用次数 |
| 失败和取消可控 | 排队取消零请求；运行取消阻止后续调用；兄弟部分失败明确呈现；已完成副作用可查 |
| 权限及额度不因分工扩大 | 越界任务／结果访问失败；并发请求不能突破共享额度；followUp 不能重置总额 |
| 上下文相互隔离 | 兄弟私有材料不自动进入另一任务；Compact 后重要约束和来源保留；Memory 停用不被任务摘要绕过 |
| 重启可解释 | 已完成结果可读，未完成标记中断；不自动重复动作 |
| Capability 真正复用 | 公司实际执行进入新服务，结构化、取消和证据仍符合原有业务契约；服务缺失的旧包仍可运行 |
| 观测与业务解耦 | Trace 缺失不阻断；模型及 Search 实际请求仅记一次；任务失败仍有安全诊断 |

调度／配额用最低成本的确定性验证，跨模块状态用集成验证；并行汇总、追加复核与公司调研至少取得对应真实模型链路证据。细化执行顺序与测试过程在对话中管理，正式文档只维护契约。
