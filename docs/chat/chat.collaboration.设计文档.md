# Chat 多 Agent 接入设计文档

版本：0.1 · 日期：2026-11-09 · 状态：首版协作机制已验收，后台真实链路与独立复核通过。

依赖 [Base.Agent 协作扩展](../base/base.agent.collaboration.设计文档.md)。本文定义主 Chat 如何使用协作机制，与 [Chat Runtime](chat.runtime.设计文档.md)、[Memory](chat.memory.设计文档.md)、[Compact](chat.compact.设计文档.md) 和 [人机交互](chat.interaction.设计文档.md) 共同构成接入契约。

## 1. 用户体验与职责

主 Chat 始终负责理解用户目标、决定是否分工、检查结果和最终答复。子 Agent 完成独立任务，其结果作为主 Agent 的输入。用户可以直接提出分工要求，也可以让 Chat 在有明确收益时自行选择。

| 组合 | 例子 | 收敛责任 |
| --- | --- | --- |
| 单项委派 | 核查一组资料，主 Agent 继续分析其他部分 | 主 Agent 检查结果后整合 |
| 并行分工 | 分别研究三家公司再比较 | 主 Agent 等待必要结果，说明缺口 |
| 串行接力 | 先提取要求，再根据要求设计方案 | 主 Agent 选择必要输入交给下一任务 |
| 执行—复核—修订 | 写出方案、独立审查、按意见修改 | 主 Agent 判断意见和返工次数 |
| 有限轮讨论 | 从产品与技术视角检查分歧 | 主 Agent 转交争议、要求依据并结束讨论 |

上述方式可以在一次任务中组合，不增加模式选择器。角色是任务说明与受限配置，不固定为调研角色。普通问答、短操作和需要密切来回确认的工作仍由主 Chat 直接完成。

## 2. 首版默认策略

下表为首版默认值；属于 Chat 策略，可经真实使用调整，不是 Base 固定常量。

| 项目 | 默认值／行为 |
| --- | --- |
| 子 Agent 并发 | 每个协作作用域最多 3 个，超出排队；主 Agent 不占这些子任务槽位 |
| 累计规模 | 最多 8 个子任务，每个任务最多 2 次后续执行；创建、追加与失败重试均累计 |
| 单次执行 | 每个子 run 最多 8 个模型轮次，遵守 Base 最后一轮无工具约束 |
| 总模型调用 | 主协调、子运行、协作中的 Compact 共用 32 次实际请求上限；预留 1 次给主 Agent 最终无工具答复 |
| 总执行时间 | 默认累计 10 分钟，主执行／等待子任务均计时；最后 60 秒用于收束及成稿，人工等待见第 4.1 节 |
| 网络额度 | 继承当前父请求的搜索／读取总额，主、子共享；派工另声明每次子运行的 maxSearchCalls，工具执行前同时受局部上限与共享总额约束 |
| 模型 | 默认使用主请求已解析的模型与思考配置；宿主执行配置可显式指定已获准快照，首版界面不增加角色模型配置页 |
| 角色与指令 | 根据任务临时生成目标、验收要求和职责；用户明确分工优先 |
| 派工深度 | 首版由主 Chat 创建直接子任务；子任务工具中不开放继续派工 |

`spawn_agent` 必须声明 `maxSearchCalls`：离线任务为 0，有明确用户限制时转入该字段；宿主将其压到父请求上限以内。每个显式 run 单独计算搜索准入次数，取消前不占额，已准入但失败的尝试保守占额。新建或追加 run 仍共享根任务总额度，不能用拆分绕过整体预算；模型是否准确提取用户的自然语言限制仍需任务验收。

总模型调用限制在开始派工前建立并包含本请求已消费部分；32 次是上限，不是必须用满或每次预留消耗。无协作的普通 Chat 保留现有预算。Provider 重试若实际产生新请求也消耗额度，后台独立 Memory 学习按原任务归属计量，不挂到子任务额度中。额度用尽保留已有成果并说明缺失，不另起新作用域绕过限制。

最后无工具轮保留已验证的上下文与证据，并在当前模型输入末尾附加宿主收束提示，要求输出已有证据支持的结论及缺口。该提示不构成新用户授权，不进入对话历史或自动学习，不增加预留轮之外的请求。

主、子同一个根任务的身份与额度跨内部续答保持不变。任务结束后的新用户请求可以引用旧结果并创建新作用域；不复活已关闭作用域的工具执行权限。

## 3. 模型可见工具与编排

为主 Chat 提供一组领域无关的工具，底层映射到同一个协调器：

| 工具 | 用途 |
| --- | --- |
| `spawn_agent` | 提交有明确目标、必要材料和结果要求的子任务；立即返回状态 |
| `send_agent_message` | 给尚未结束的子任务补充说明；回执区分已排队与已交付 |
| `followup_agent` | 对已结束任务追加一次工作，例如依据复核意见修订 |
| `wait_agents` | 等待指定 run 的变化／完成；使用游标，避免反复轮询 |
| `list_agents` / `read_agent_result` | 查看任务状态、读取有界结果或细节 |
| `cancel_agent` | 取消指定未完成子任务 |

工具不允许模型传入真实 API Key、任意宿主 owner、无限预算或直接扩大权限的实现对象。执行配置由宿主从父请求与已准入配置中解析。

任务 ID 限于当前请求作用域；下一条用户消息需要复核先前成果时，创建新有界子任务并显式传入已保存材料。旧 ID 返回可理解的作用域提示，不重启旧任务。最终汇总应完整保留成果中的日期、数值与限定条件，并形成自包含答复。 子任务已收集的来源随正文一并交付：自动续答、`list_agents` 和 `read_agent_result` 都保留 `sources`，不依赖子模型在正文中再次抄写 URL。来源交付完整不等于事实已核实，主 Agent 仍需区分来源原文与推断。

派工工具经过现有 ToolRunner 校验、取消、审计和安全投影。多个 spawn 按 Pi 原顺序执行，但其子任务各自异步运行。主 Agent 可以继续独立工作；需要结果时再 wait。

依赖式任务先读取上游已完成产物，再显式传给下游；兄弟任务之间不自动共享上下文。独立审稿必须收到实际初稿并针对它提出意见，修订任务必须收到待修改稿与审阅意见。运行中的补充通过 `send_agent_message` 核对交付，已结束任务通过 `followup_agent` 追加。用户要求交回原助手时复用原 taskId；新建任务并赋予相同角色名称不代表同一任务续接。验收检查实际交接内容与执行结果，不能以任务名称或完成数量代替。此顺序由 Chat 编排指引约束，Base 不根据自然语言猜测依赖关系。

### 3.1 等待与最终答复

主 Agent 的工具循环仍按 Pi 自然停止及限轮执行。子任务结果先持久化，通过内部协作结果通道进入下一次安全上下文投影，包含 runId 和事件游标，重复投递不能重复消费。

主 Agent 拟结束而必要子任务仍未结束时，Chat 将本请求保持为等待中，收束当前工具调用／结果后等待；不把这段临时回复标成最终答案。结果到达后合并一次续答输入，再在同一作用域及剩余额度内继续。续答不是新用户消息，不触发标题生成或 Memory 学习。

首版所有已派出的任务默认属于需收束工作。主 Agent 若决定无需某项结果，应显式取消。进入最后 60 秒或只剩预留模型请求时，停止新派工并取消剩余工作，在剩余时限内使用预留请求输出已有成果及缺口。硬截止时间到达仍未完成时，终止成稿请求，保存成果并显示确定性超时提示，不再调用模型；网络失败同样保留成果。用户点击停止时直接取消，不额外请求模型成稿。

每次续答按游标只消费新结果，可合并已到达的一批完成事件；等待期间不忙轮询 Provider。工作已结束但后续答复失败时可基于已提交结果继续，不能重复启动已完成子任务。

## 4. 工具权限与人机交互

首版 Chat 子 Agent 默认拥有完成任务所需的只读／计算工具子集。联网关闭时子任务也不能发起搜索或网页读取；可以使用获准的历史结果。Capability 可见性仍取本次启动加载目录。

读能力资料或调用只读 Capability 操作时，要经过现有发现、动作 Schema 和权限校验；不能只凭工具名或模型自称“只读”放行。混合读写的通用调用工具须按具体动作过滤。不能证明安全的操作交回主 Agent。

Chat 的 Capability 工具投影为 `completed` 结果附加宿主生成的 `agentGuidance`，说明业务结果已经可用、分页与截断应依动作契约判断，并提示避免为证明完整性而重复查询。业务 `data` 保持原样；后台任务受理、等待用户和动作说明不标为完成。此反馈供主、子 Agent 共用，不直接终止工具循环；用户要求刷新、存在后续分页或仍缺少必要信息时可以继续查询。

业务写入、删除、提交调研、修改记忆等需要影响用户数据的操作，由子 Agent 返回建议，主 Chat 经过原有动作与 HITL 路径执行。已有用户授权继续有效，不因“由子 Agent 建议”再要求一次确认。子任务的建议或摘要本身不是用户授权。

这使首版支持分析、调查、产出文本和独立复核，副作用仍有一个明确入口。将来开放子 Agent 直接执行写入时，须复用同一权限及确认回执，补齐冲突与幂等保障后再开放相应工具。

### 4.1 等待用户与恢复

HITL 的问询／确认仍由主 Chat 发出。若进入等待时存在子任务，先停止派工，取消并收束这些子任务，保存已经提交的结果；等待用户期间不继续后台子运行，也不由迟到结果唤醒主 Agent。

`scopeId` 独立于单次执行的 requestId。交接时将 scopeId、原始 owner、累计消耗、剩余执行时间和结果游标绑定到可信交互记录；现有请求的 finally 可以释放运行实例，但不能删除逻辑作用域或结果。只有交接检查点保存成功、活动执行已收束，才进入持久化 `waiting_user`。收束结果不明时记录 interrupted，不伪造可无损恢复的暂停。

等待用户期间暂停执行时间计时，已消费的模型／网络／任务额度不退还。收到既有机制确认有效的用户回复后，通过新 requestId 关联同一 scopeId，并以剩余额度重新装配执行片段；取消过的子任务不会自动重启。需要重新分工时由主 Agent 显式发起，累计次数继续计入原作用域。

用户拒绝、取消整轮或交互失效时关闭作用域。若在人工等待期间重启软件，沿用已持久化交互的正常恢复路径；若在执行期间意外退出，按 interrupted 处理。两者不能混为自动续跑。迟到事件只能更新原 task/run 的诊断，不改变用户交互状态。

## 5. Memory、Compact 与持久化

- 任务输入包含目标、必要约束、材料引用和结果要求；默认不复制完整主 Chat 历史。为减少漏传，可由宿主补充当前用户请求及有效的任务约束投影。
- 子 Agent 使用独立 transcript 与 Compact 检查点。复用 Pi 安全切点、摘要生成与输入预算机制，Chat 的策略通过适配器注入；不要求 Base 导入 Chat 文件。
- 派工时将 Memory 引用与普通任务材料分开。每次模型调用重新解析有效记忆，摘要使用未注入长期记忆正文的安全历史；停用／修改／删除后按既有 Memory 规则生效。
- Memory 运行时只读回执保留对应查询／读取参数，前提是调用与回执匹配且引用仍有效；空结果同样保留查询依据，避免混淆已经完成的检查。持久化与写入参数继续脱敏，已失效或已省略的内容不恢复。
- 子 Agent 不自动学习长期记忆。主 Chat 的原始用户交互仍按既有规则学习，任务输出、自动续答和讨论消息均不作为新用户事实来源。
- 主 Chat 的 Compact 保留子任务的目标、已提交状态、摘要和结果引用；压缩不能使任务状态回退，也不能重新运行完成动作。运行状态从任务仓储校准，不能只相信模型摘要。

Chat 持久化任务／run 元数据、已交付命令、结果和安全 transcript 引用，绑定 conversationId 与父 requestId。子任务不是侧栏中的新对话，不触发独立标题。

切换页面不取消运行。重启后恢复已有结果与状态展示，未结束工作标记中断；用户决定是否重试或继续分析已有成果。删除原对话时同步清理所属子任务内容，活动对话沿用现有删除限制。

## 6. 界面与可观测性

复用每条助手消息下的工具活动区域，增加可折叠的协作活动：默认只显示任务名、等待／运行／完成／失败状态及总体进度；展开后可查看任务要求、必要工具活动、结果摘要和错误。

不逐 token 将所有子任务正文平铺到 Chat。需要详细结果时通过同一展开区域有界读取；敏感参数、隐藏推理及内部管理 ID 不进入用户正文。主 Chat 最终回答给出结果及有价值的局限，不逐项叙述内部派工过程。

沿用现有停止按钮取消整个当前请求及其未完成子任务；展开区可取消单项，主 Agent 也可通过工具取消。暂停等待结果时保留可停止状态。切换对话再回来，任务状态和最终结果完整恢复，迟到事件只更新所属请求。

主 Agent 的工具前说明和内部续答前的文字保留为执行过程，运行中展开，完成后可折叠查看；最终答案独立展示，切换会话后可恢复。子 Agent 使用只读执行与记忆指引，不继承主 Agent 的派工职责。

Trace 可查看父请求—子任务—模型／工具调用关系；宿主仅从已校验并持久化的协作检查点登记子 run 归属，拒绝未登记及跨根事件。Usage 统计每个实际请求一次。状态展示与业务恢复来自持久化任务，不依赖 Trace 启用或正文采集。资源准入拒绝保留明确的预算或时限原因，不被模型适配层归并为 Provider 故障。

## 7. 接入位置与兼容

| 当前位置 | 接入责任 |
| --- | --- |
| `packages/base/src/agent/` | 新增可选协调器和中立契约，保留一次性执行入口 |
| `apps/desktop/src/worker/assembly.ts` | 装配运行作用域、共享预算、配置和工具权限 |
| `apps/desktop/src/worker/agent/pi-chat-agent.ts` | 主 Agent 协作工具、子执行器、结果续答与取消桥接 |
| `apps/desktop/src/worker/chat/` | 子任务安全 transcript、Memory／Compact 适配、主上下文结果引用 |
| `packages/application/src/chat/` | 请求生命周期、等待／续答、人机交互与持久化桥接 |
| `packages/persistence/src/` | Chat 子任务元数据、检查点及结果存取，迁移使用 Base.Database |
| `apps/desktop/src/renderer/` | 复用工具活动区展示与恢复，主消息与子状态分开更新 |
| `packages/capability-sdk/src/services.ts` | 独立的可选协作服务入口；公司包按 Base 设计验证实际复用 |

关键兼容点：当前 `ChatService` 的 completed 事件会完成助手消息并触发后续学习。子任务完成必须走专用事件，不能把同名事件加上父 requestId 后直接送入原消费流。只有主协调完成才结束整轮用户请求。

历史会话没有子任务记录时继续使用现有显示。新字段与迁移增量添加，不修改旧报告、记忆或 Compact 原记录。无协作请求应保持现有工具循环和取消行为。

## 8. 验收与交付边界

| 场景 | 用户可观察的预期结果 |
| --- | --- |
| 普通请求 | 直接完成，不为了使用新功能额外派工 |
| 明确要求并行调查 | 多个任务有独立过程，主回复实际综合各方结果与来源 |
| 先产出再审查 | 审查内容具体对应产物，修订结果回应有效问题；达到轮次上限可结束 |
| 中途补充要求 | 消息有明确交付状态，最终结果体现已经接纳的要求 |
| 取消／部分失败 | 停止后不再派工；成功结果保留，失败清楚，任务不被当成整轮成功 |
| 会话切换与重启 | 当前会话不被别的子任务污染；结果可读，中断任务不自动重放 |
| 长上下文与记忆变更 | 子任务整理后仍保留约束；不通过摘要恢复已失效长期记忆 |
| 副作用与授权 | 子任务不能绕过原有确认；主 Chat 获得有效授权后也不重复确认 |
| 分工后等待用户 | 未完成子任务先收束；等待期间无后台请求；确认后使用剩余额度，已完成操作不重复 |
| 使用成本 | 主子共享真实额度；Trace 可定位失败，Usage 不重复统计 |

开发顺序为：协作执行核及关键不变量 → Chat 委派／并行和展示闭环 → 追加／接力／复核与上下文管理 → Capability 实际接入及联合验收。每段保持现有单 Agent 路径可运行。只在关键路径自验完成后交付可直接打开的应用包，由用户验收本批体验；按项目交付规则统一整理提交。

本轮验收覆盖调度、依赖交接、原任务续接、过程恢复及 Trace／Usage 关联。`completed` 表示执行结束与结果已保存，不等于产物满足业务要求；模型仍可能漏交正文或增加待确认事项，主 Agent 的产物检查与纠偏效果需单独评估。
