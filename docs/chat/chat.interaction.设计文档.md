# Chat 人机交互设计文档

版本：0.4 · 日期：2026-09-24
状态：本轮任务范围、过期请求与语言修复已完成定向本地验证；最终类型检查、构建、安装包同步与用户手工验收由本轮交付流程记录。此文档不宣称旧版本安装包已包含本轮修改。

## 1. 目标与已确认方向

为 Chat 提供 Human-in-the-loop（人在环中）交互：需要用户决定时停下来，获得回应后继续。Chat 与主 Agent 是同一概念。

- 区分“询问用户怎么做”和“确认是否执行”，不固定三个选项，不是账户鉴权。
- 操作确认可服务于 Capability 调用，以及以后文件写入、修改、删除等工具；不按公司调研业务定制。
- 对有编辑界面的操作，复用 Capability 原有真实表单，移除独立只读预览页。模型和用户修改同一份草稿，左右两个确认入口处理同一次操作。
- 用户可以点左侧、点右侧，或在 Chat 明确确认；修改内容后旧版本确认不能继续执行。
- 交互提示属于发起它的消息，历史可读；不固定到输入框上方，不抢其他会话的焦点。
- 这是 **Chat 专属机制**，不新增 Base.Interaction，不给 Capability 内部调研循环强加用户交互。

实现跟踪见 [分步计划](../superpowers/plans/2026-09-23-chat-human-interaction.md)；本文件的“拟定”段落保留设计语义，实际公开接口以 SDK 和开发指南为准。

## 2. 实现状态与缺口

截至本次离线联验，Chat 已有 question/approval 协调器、主进程可信回应、Capability 动作网关适配、按会话保存的修订与恢复描述符。包可选注册表单目录和草稿提供方；关联 UI 接收绑定单个待办的编辑桥，调用 `beginEdit`、带预期修订的更新/转换和回应。没有表单声明的公开动作仍可走只读确认卡。`tests/capabilities/form-protocol.test.ts` 仅证明一个便签示例包在离线环境下的发现、共同编辑、单次执行及禁用后启动快照排除；它不等于所有第三方包或全部公司表单已手工验收。公司表单实际登记清单见 [手测说明](../manual-tests/2026-09-23-chat-human-interaction.md)。

多阶段 `afterAction` 由注册表单提供方传递给宿主，并须据真实回执创建下一次独立确认；完整导入链路仍需联验。重启中断、系统保存对话框、真实模型文字确认及完整公司向导仍需按手测说明检查，不以离线夹具代替。

技术边界：包草稿推进与 Chat 下一阶段描述符分属不同持久化写入。若进程恰在真实动作成功后、下一阶段描述符落盘前崩溃，恢复时可显示上一动作回执，但不能自动重放写操作来补下一阶段；用户需重新核对并打开表单继续。首版不宣称此窄窗口具备跨存储原子性。

页面联动补充：Capability 表单快照可提供 `parentView`，公司包的 ViewProvider 将表单引用解析到该真实业务页后再挂载原表单。无表单动作使用已有 `presentOperation.target` 与 `autoOpen` 展示上下文；Chat 不读取主题或公司路由字段。执行回执在交互终态落盘后发布，沿用原请求的导航 generation；切换会话或主动离开后只保留结果入口，不抢回页面。Renderer 在结果导航前核实绑定交互已终结，释放该表单的 dirty 保护，仍保留其他人工编辑保护。

同一交互的执行回执通过可信 invocation→receipt→interaction 关联投影到原卡，后台任务使用完整 TaskRef（含 capabilityId）与可信回执关联在原卡持续更新；无关联的历史回执和其他操作继续独立显示。问题回答收起为紧凑回执。公司表单遮罩限定在 Capability 面板，Chat 可继续输入；表单内确认、取消和向导按钮不计作主动离开页面。

## 3. 方案选择与职责边界

### 3.1 选择：Chat 协调交互，原工具/业务仍负责执行

不采用“每个 Capability 自建确认系统”：否则工具和能力的确认重复实现，左右状态容易分离。

不采用“全部塞入 Pi Hook，等待一个 Promise”：它可以阻止工具执行，但无法独立解决跨轮修改、持久状态、两边编辑和会话恢复。

采用 **Chat 交互协调器 + Pi 执行前拦截/交接 + 可选业务编辑适配**。三者不是新增架构层级，只是在当前 Chat/Capability 边界内分工。

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| Chat 交互协调器 | 问题、确认请求、用户回应、版本绑定、等待/恢复、会话归属 | 公司字段、文件编辑算法、调研流程 |
| Chat 工具/执行适配 | 向模型提供提问入口，提出待执行操作，交接及回传结果 | 自行批准、凭模型文本绕过策略 |
| 工具或 Capability 执行端 | 参数校验、实际操作、幂等/结果查询 | Chat 历史、消息卡布局、自然语言意图识别 |
| Capability 表单/草稿适配 | 真实表单、业务草稿、修改校验和版本 | 导入 Chat 内部状态、生成批准票据 |
| Chat UI | 问答卡、确认卡、用户输入与状态投影 | 再保存一套独立待执行参数 |

协调器的领域代码拟归 `packages/application/src/chat/interaction/`，主进程接线归 Chat 目录，UI 归 Chat 组件。共享 DTO 可放现有 contracts，持久化实现可放现有 persistence；物理共用包不改变 Chat 的领域归属。Base、Capability 不能反向导入 Chat 实现。

Capability 独立页面仍可正常使用：没有关联 Chat 待办时，用户按原有表单流程提交，不创建 Chat 记录，也不要求存在 Chat 会话。

## 4. 两类请求，不用按钮数量判断语义

### 4.1 询问（question）

用途：补充缺失信息、选择方案或确认偏好。由模型通过 Chat 专用提问工具发起。

- 支持纯文本输入，或若干选项并允许自由输入；选项数量不固定为三。
- 首版每次一个聚焦问题，选项可选；最多六个短选项，避免变成配置页。该上限是界面约束，不是业务分类。
- 推荐项只作提示，不自动提交；不强加“同意/拒绝/用户输入”三个通用选项。
- 用户可以在卡内回答，也可在 Chat 回答，答案回到原会话供模型继续推理。
- 回答仅代表信息，不产生执行批准。选择“产品与技术”不等于批准付费调研。
- 对缺失信息仍有合理默认值的低风险任务，不强制询问；不把所有任务改造成问卷。

### 4.2 操作确认（approval）

用途：对象、影响及输入已经明确，需要用户同意执行。

- 默认按钮为“确认”与“取消”；可采用可信的业务动词如“确认创建”，不强制第三个按钮。
- 通过正常 Chat 输入修改意见，不需要常驻第三按钮；以后可以增加“提出修改”快捷入口，但语义仍是反馈而非批准。
- 执行策略/动作声明决定哪些操作必须确认。模型可以主动要求更谨慎的确认，不能免除强制确认。
- 确认可覆盖当前具体操作或一次已展示的有限任务范围，不提供永久允许或会话内任意操作授权。
- 拒绝不等于工具故障，不应触发自动重试或让模型换个同义调用继续执行。

确认不是账户鉴权，也不能突破权限、沙箱、当前工具开放范围或 Capability 启用状态。

### 4.2.1 一次任务范围确认

`propose_actions` 接受 `firstCall + rules + endCondition`。每个规则冻结动作、契约、包版本、固定输入和执行次数（1–10），仅允许包 `taskAuthorization.mode=scope` 声明的顶层动态字段；资源字段只能固定或绑定此前单次规则成功回执中由包声明的输出路径。最多 10 条规则。所有未声明动态的输入精确匹配，不允许额外字段。模型只提出范围，确认卡由宿主和包只读呈现函数显示目标、动态选择、次数、资源消耗与结束条件；普通按钮或明确文字确认一次后才激活授权。

授权仅驻留主进程内存，可跨本任务自动恢复轮次。每项仍经过原表单、协调器版本核验、独立回执、完整输入校验与一次性网关票据，最终异步校验后再次检查授权。删除允许显式列明的精确对象且每条单次，不允许动态字段或回执资源绑定；添加权限不推断删除权限。完成、取消、失败、新用户任务、编辑或重启撤销授权；问题答案可继续原任务，但不新增权限。人工编辑剥离任务范围，回到单项确认；需要连续执行时重新准备范围。已发出动作保留真实回执，不假装回滚。

问题答案、引用、条件、否定或混合修改语句不产生授权。没有当前已展示范围时，先前口头“无需逐项确认”仍需先准备范围并确认一次，不宣称完全无需确认。后续参数可以来自结果，但搜索内容和模型文本不能授予权限或充当可信资源回执。包未声明支持则保留逐项确认；旧 `exact_input` 清单兼容入口仍仅执行完整冻结输入。公司包支持指定主题创建→发现公司→导入、已授权识别→同表单导入，以及精确公司移除→精确主题删除。通用 Chat 不包含这些业务字段。

请求开始时绑定交互代数；人工推进后旧模型的提案、草稿写入和有副作用调用被拒绝，异步准备及最终网关分发前都复核。已有待确认卡时不启动恢复模型，保留全部回执，处理完后合并当前事件一次恢复。恢复事实放入上下文的数据区域，不作为新用户意图；真实用户消息单独提供语言锚点，覆盖工具前说明与最终回复。持久化正确处理 `text_reset`，不会复活已撤回的工具前言；不使用字符检测删除有效回答或额外调用模型翻译。模型遵守语言指令仍需实机验收。

### 4.3 触发示例

| 情况 | 处理 |
| --- | --- |
| 用户未说明研究方向，且无法合理推断 | question：选方向或输入要求 |
| 新建主题字段完整 | approval：展示真实表单与确认/取消 |
| 用户要求把备注深化 | 修改当前草稿，更新确认版本，不批准 |
| 只读查看已存在报告，当前规则允许 | 直接执行，不必询问/确认 |
| 将来工具计划删除文件 | 执行策略要求 approval，展示准确文件对象 |
| 用户讨论“删除功能应该怎么做” | 普通回答/设计讨论，不创建删除待办 |

## 5. 请求模型与唯一状态源

以下为拟定概念契约，不代表已经发布的 SDK 字段。

所有交互共用：`interactionId`、`kind`、`conversationId`、`sourceRequestId`、交互修订号、创建/更新时间、状态。内部 ID 不作为用户可见正文。

question 额外包含问题文本、可选选项、是否支持自由输入、回答结果。它没有待执行动作绑定。

approval 额外关联：

- 待执行操作描述符、调用身份、参数快照或业务草稿引用。
- 当前内容版本、可读确认摘要、执行回执 ID。
- 可选真实表单目标及编辑能力；无表单的工具可展示摘要或差异，不强造表单。
- 响应来源：Chat 按钮、关联表单按钮、真实用户消息。

**Chat 是交互状态的唯一权威；业务草稿是内容的唯一权威。** 两者分别管理不同事物，不是左右各保存一套内容。Chat 可缓存当前版本的只读摘要，但提交前必须重新验证草稿版本。

编辑时允许表单有尚未同步的临时输入；此时显式标记同步中/待修正，不能批准旧内容。已同步版本才是左右按钮共同确认的内容。

主进程产生并验证来源、会话、版本及执行票据；模型不能通过伪造 `approved: true` 等工具参数制造批准。

## 6. 生命周期

### 6.1 询问生命周期

`等待回答 → 已回答 / 已取消 / 已失效`

回答落盘后，安排原会话继续；处理过的同一个回应不能再次恢复执行。用户取消问题时，向模型回传取消，不把未回答当默认选择。

### 6.2 操作确认生命周期

`待确认 ↔ 编辑/同步中 → 待确认 → 执行中 → 已完成 / 执行失败 / 结果待核实`

另有 `待确认 → 已取消 / 已失效`。审批与实际执行分别记录，但界面不需要展示所有内部过渡。

- 用户确认时，原子地认领该交互的当前版本与执行回执；同时点击左右按钮，只能一方成功认领，另一方返回同一状态。
- “已同意”不是“已完成”。等待服务返回期间，两侧都显示执行中并禁止重复提交。
- 后台任务被接受后，交互可显示已提交，实际进度来自原任务记录；不能把接受任务写成报告完成。
- 参数修订不会重新创建一排历史确认卡；原卡更新并注明内容已更新，内部保留必要版本/回应记录。
- 真实执行失败显示失败原因；重新尝试是新的执行尝试，是否再次确认按当前内容与策略核验，不自动无限重试。

### 6.3 会话内串行边界

首版每个会话同时只有一个需要人回应的活动交互。一个确认中可以接收修改意见、解释请求和无关聊天，不锁住输入框。

不同会话可分别有待办。若模型要在同一会话发起第二个待办，不覆盖第一个；返回已有待办提示，先完成/取消或明确替换。替换须使旧请求不可再执行。

同一模型批次内遇到待用户回应，后续未开始的工具不执行，也不自动排成一串确认；继续后由模型依据最新状态重新决定。已经完成的工具不能重放。

## 7. 模型、用户与真实表单的共同编辑

### 7.1 新建主题闭环

1. 模型提出新建主题的输入；执行适配器创建关联交互和包内草稿，不创建真实主题。
2. 打开原有“新建主题”表单，以草稿预填。普通手动入口与 Chat 入口复用同一表单组件、校验和业务提交服务。
3. 左侧显示当前内容摘要和确认/取消；右侧仍是用户熟悉的字段与确认/取消。
4. 用户改字段或模型修改草稿后，版本增加，另一侧接收更新。
5. 任一入口确认当前有效版本，通过同一个批准/执行入口提交。关联表单不再另走一次原始 create API。
6. 服务成功后，左右显示同一个回执，右侧进入真实主题页面。取消则解除待办，不留下业务主题。

独立 `topic-preview` 页面和为其维护的展示分支删除；已有历史链接可以安全显示入口已失效，不能为了兼容重新维护第二套表单。

### 7.2 业务包提供什么

包可为动作提供可选编辑适配：准备草稿、读取当前草稿、基于版本更新、校验/取得可提交输入、释放草稿及真实表单目标。

具体字段和业务存储由包维护；Chat 不接管公司/研究范围类型。现有 DraftRef/ViewRef 优先复用，只有实现这些语义缺少的最小部分才扩展 SDK。

关联表单通过宿主提供的窄交互桥读取状态、提交带版本的修改、回应确认/取消、订阅变化。桥绑定实际待办和挂载包；不接受任意会话 ID 来修改其他待办，也不向包暴露批准票据。

包没有编辑适配时：仍可执行、仍可使用必要确认；修改要求可使旧请求失效后重新提出输入，不生成模拟页面。纯后台 Capability 不必实现表单。

### 7.2.1 协议驱动的全部表单复用

Capability 在包内注册表单目录及操作与表单绑定。启动只装载已启用包的声明；宿主不扫描 React/DOM 猜测功能，不按公司调研 ID 或字段名分支。注册包含稳定表单 ID、关联操作、按需读取的输入约束/说明、草稿提供方和真实 ViewRef；沿用 Action/DraftRef/ViewRef，不另造业务路由。

草稿提供方统一支持准备、读取、版本化更新、校验、释放。多步骤表单提供当前步骤及允许的转换，模型不能直接篡改内部步骤状态。下一步、上一步、保存当前行修改不等于批准最终执行；步骤内搜索/解析等动作仍遵守原权限与确认策略。

若中间步骤本身需要批准（例如付费识别公司文本），该步骤作为独立动作获得确认。提供方可通过可选 `afterAction` 消费宿主传回的真实执行回执，推进同一草稿并声明下一动作；宿主结束上一确认后为下一动作新建确认，不继承批准。界面仍复用原向导，不新增模拟页面；普通步骤转换不得自行执行需确认动作。

人工和模型使用同一表单输入模型、校验、步骤转换、提交服务。组件本地只保留未同步输入缓冲；不另写 Chat 专用表单、镜像草稿或每表单的宿主适配。普通人工使用无需 Chat 会话。文件保存对话框保留平台权限，不变成模型可任意填写的文件路径。

“新包无需额外逻辑”指符合协议后无需修改宿主或 Chat；包作者仍需在包内声明和维护已有操作/表单的绑定。未声明的旧包保留原调用能力，但不自动获得可视编辑；声明损坏只阻断对应编辑入口，不阻断主 Agent。说明按需加载，不全量放入上下文。

### 7.3 编辑竞争

- 用户开始输入时，关联 UI 立即将该待办置为编辑中，禁用 Chat 确认；原表单确认先等待字段同步完成，不能执行旧值。确认事件与编辑事件经同一主进程顺序处理。
- 用户点击确认时先刷新待同步字段，再按最新版本提交；同步/校验失败时保留输入，不能使用旧值执行。
- 所有更新带 `expectedRevision`。模型读到旧版本后，用户又改过，模型更新应返回版本冲突，重新读取后再修改，不能覆盖用户编辑。
- 首版不做自动三方合并。模型收到“仅深化备注”时只更新该字段，其他字段保留。
- 多窗口/并发消息冲突返回明确的“内容已更新，请核对”，不悄悄替用户批准更新后的版本。
- 获批进入执行中后锁定本次输入。后续改动是新操作；原操作结果如实展示。

## 8. 三种回应入口与自然语言确认

### 8.1 左右按钮

Chat 按钮直接回应当前交互版本；右侧按钮回应其绑定版本。右侧是可信用户点击，但包只能通过宿主桥提交决定，不能自行构造模型批准。

关联表单即使在用户切换会话后仍可归属原会话；回应只能更新原会话和原待办，不能写进当前另一会话，不能自动切换 Chat 焦点。UI 清楚显示它属于原操作。

### 8.2 Chat 文字回应

主程序在收到真实用户消息时捕获当前待办及内容版本；模型输出、工具结果、网页和引用中的“同意”均不构成用户回应。

首版采用保守的两段处理：

1. 对唯一明确待办，独立、无附加条件的“确认”“确认无误”“同意执行”等明确回应，由 Chat 可信入口转换为带版本的决定；提交时再次核验未发生编辑。
2. 其他输入作为反馈交给模型理解，可解释、提问或更新草稿。含歧义、否定、引用、条件或修改要求的消息不产生直接批准。不能只因文本包含“同意”就执行。

例如“把备注改完再确认”不批准旧内容；“同意你的设计”没有具体待执行操作时也是正常聊天。更复杂但看似同意的表达，首版可以请用户点现有按钮，不以模型的判断替代用户授权。

模型负责理解修改要求，不获得一个可任意调用的“替用户批准”工具。按钮提交和自然语言确认最终都走同一个可信决策入口。

### 8.3 问题答案

question 的选项点击或普通文本回答只生成答案。模型可据此形成下一步操作，若该操作需要批准，再走 approval；不能把回答问题的一次点击跨用为批准。

## 9. Pi 接入与恢复执行

### 9.1 复用范围

本项目实际安装 `@earendil-works/pi-agent-core 0.84.3`。它提供参数校验后的 `beforeToolCall`，支持异步检查及阻止执行；当前执行器已使用它处理预算和结束边界。Pi Coding Agent 的 `tool_call`、`ctx.ui` 及 permission-gate 示例提供参考，但不能当作本项目已经具备的终端 UI 接口。

本次不升级 Pi、不引入整个 Coding Agent、不自建替代 Loop、不顺带迁移到另一套 Harness。

### 9.2 不能只增加一个挂起 Promise

首次触发交互时保存待办，让本次 Chat 执行片段以“等待用户”结束，输入框恢复可用；不是一次失败，也不是要求模型继续猜测/不断重试。

Pi 当前工具调用必须有匹配的结果。交互适配返回结构化 `awaiting_user` 结果，记录未执行；之后恢复不能给同一个 toolCallId 再塞第二个结果。用户决定与真实执行回执作为新的可信 Chat 事件进入上下文。

若当前模型批次还有工具，顺序执行边界标记其未执行，并保持调用/结果配对。不得把它们解释成已经获准。Pi 的单个 `terminate` 提示并不保证任意混合批次立即结束，不能只设置一个字段就宣称支持暂停。

实现时需由 Chat 执行适配提供明确的交接信号：结束当前批次后不再发起下一次模型请求，不进入“额度耗尽后的最后一轮强制总结”。通用执行器如需增加窄控制口，只认识中性的交接/结束信号，不导入交互 ID、审批状态或 Capability 字段。Capability 内部调研未注入该口时行为不变。

已核对当前安装的 Pi 0.84.3：可用 `shouldStopAfterTurn` 在完整工具批次的 `turn_end` 后、下一次模型调用前结束循环。实施优先复用该钩子，组合现有 `beforeToolCall` 拦住尚未执行的同批工具，保存完整调用/结果配对；执行器随后走独立交接终态，不进入最终答案校验。不以单个工具的 `terminate` 或中止请求替代正常交接。

### 9.3 回应后继续

- 回答问题：记录答案，以唯一回应事件恢复原会话一次。
- 确认操作：可信协调器先执行已批准的原操作，保存真实回执，再将结果交给模型继续；不能依赖模型再次调用同一写操作。
- 拒绝：向模型回传用户拒绝，允许解释或提出替代方案，但不得自动重复同一操作。
- 修改意见：开始新的 Chat 执行片段，模型通过同一编辑适配更新草稿，随后仍等待确认。
- 当前会话正运行别的片段时，后续事件进入原会话串行队列，不同时启动两个模型循环；事件按 ID 去重。
- 后台任务“已接受”只恢复一次；后续进度更新原卡。是否完成后自动分析沿用用户明确意图，不轮询、不每次进度都调用模型。

提问工具拟名 `request_user_input`，仅向 Chat 开放；模型编辑待办的工具只能读取/更新其有权限的当前草稿，不能批准。具体 SDK/IPC 命名在实施计划中确定，不把内部 ID 或版本呈现在普通回答里。

## 10. UI 与持久化

### 10.1 呈现

- question：短问题、按需出现的选项/文本框；不显示确认操作的风险口吻。
- approval：准确操作摘要、可选实际影响/差异、确认与取消。已有真实表单时，字段不在 Chat 再渲染一整套编辑器。
- 编辑/同步中有轻量状态，Chat 确认暂不可用，原表单提交等待同步；不要把暂未完成输入报成全局错误。
- 已回答、已提交、已取消和结果保留在原消息下方，以紧凑状态显示；不额外重复生成一段相同助手正文。
- 模型正常回复仍流式；等待用户不显示模型持续思考的转圈。
- 自动打开和结果页联动沿用当前会话/手动导航保护；用户主动离开后不因进度反复拉回。

### 10.2 持久化与恢复

Chat 存储交互记录、当前修订、回应来源、执行/恢复回执，以及必要摘要。业务字段继续存在包的草稿中；记录不包含 API Key、系统批准票据或无关上下文。

- 切换会话不取消待办，返回后恢复显示。
- 重启后 question 可继续回答；approval 保留历史和草稿引用，但旧批准不可自动执行。核验工具/包、输入版本及权限后重新激活确认；核验失败显示原因。
- 执行中退出：先查询原回执。已完成则恢复结果；结果未知显示待核实，禁止自动重放非幂等写操作。首版不承诺跨进程崩溃的绝对 exactly-once。
- 执行前重新核验业务对象/文件版本。文件内容或动作契约变更时必须重新确认，不能拿旧批准覆盖新对象。
- 删除会话按现有规则清理关联交互；已存在的业务成果不因此删除。已在运行的业务任务仍按现有任务语义处理。
- 草稿取消/失效由其提供方释放；只保留必要历史摘要，不无限积累预览副本。

普通等待不使用现有五分钟安全票据作为 UI 倒计时。用户确认后再形成短期、单次执行许可；超时、包卸载或权限撤销时重新核验，绝不静默放行。

## 11. 最小交付范围与非目标

首版范围：

1. Chat question/approval 两种请求与通用消息内 UI。
2. 可信回应、版本失效、防重复、等待/恢复及会话归属。
3. 接回现有 Capability 操作确认，不破坏无编辑适配的包。
4. 按统一协议接入公司调研全部适用表单及多步骤向导，复用已有组件和提交逻辑；移除旧预览页。新建主题仅为首个联调案例。
5. 明确工具接入契约，并用假文件工具验证其业务无关性，不在本批新增完整代码编辑功能。

非目标：复杂审批流、多级审核、角色权限系统、全局永久批准、多人实时协作、通用低代码表单生成器、自动识别无协议的任意页面、自动恢复重放未知写操作。

默认决定：每会话一个活动交互；问题按需选择/输入；批准仅本次；修改后重新核对；明确且唯一的自然语言确认可用，歧义不执行。

## 12. 必要验收

只做必要功能验证，不引入大规模细节测试或真实 API 消耗：

1. 询问能以选项/自由文本回答并继续，回答不产生执行批准。
2. 新建主题真实表单预填；模型只改备注、用户再改主题，两边最终内容一致。
3. 点击左右任一确认或明确文字确认，同一版本只创建一次；重复回应不重复执行。
4. 编辑竞争、未同步输入、旧版本按钮与文件版本变化均不能执行旧内容。
5. 取消、输入修改意见、无关聊天不会被当作同意；问题答案不会跨用为批准。
6. 等待时可继续输入，Pi 不空转、同批后续工具不偷偷执行，继续时历史工具调用/结果配对有效。
7. 切会话/重启恢复原待办，迟到回调不污染另一会话；执行结果未知时不自动重放。
8. 无 Capability/无表单适配时 Chat 询问与假工具确认仍工作；Capability 自身调研循环无新增等待行为。
9. 表单清单全部完成注册与复用；多步骤推进不等于最终批准；导出保留系统文件选择。
10. 独立业务示例包不改宿主/Chat 即可完成发现、打开、编辑与提交；禁用重启后不再暴露。

自动验证通过后打包交用户手测真实交互；本设计阶段不提前执行上述测试。
