先把目标与边界说清楚，一次授权一个可验收批次。让 Agent 负责实现与自验，把你的注意力留给产品效果和关键取舍。

小步实现发生在批次内部。每个小步完成后，Agent 继续推进已授权工作；到达约定成果或真正的暂停条件时，再集中交接。

01 / QUICK START一分钟使用法

  1. 说清你想看到什么给出使用场景、期望结果与当前问题。用具体操作描述成功，例如“返回列表后，筛选条件仍然保留”。
  2. 把关键选择一次谈拢和 Agent 确认本批范围、成果、必须保留的行为、验证方式及暂停条件，然后明确授权执行。
  3. 让 Agent 完成工程闭环Agent 实现、检查、定位失败并修复，汇报有意义的进展。普通修复无需再次审批，进度消息无需回复，也无需反复说“继续”。
  4. 拿着交付结果集中体验沿约定路径手测，反馈阻塞、本批优化和下批想法。确认效果后结束这一批，下一批再约定范围。

“继续推进”以当前任务运行和已有授权为前提。关闭或退出对话后是否继续，取决于实际运行环境；这份约定本身不会创建后台任务。

02 / OWNERSHIP各自负责最擅长的判断

你：产品目标与效果

  • 提供场景、优先级、限制与可用资料。
  • 决定会改变方向或范围的关键取舍。
  • 体验交付成果，判断是否解决实际问题。
  • 反馈期望、实际和复现路径。

主 Agent：工程验收与交付

  • 澄清契约、规划批次，组织实现并复核。
  • 按风险选择有效验证，持续处理相关失败。
  • 保留定位证据，说明真实阻塞与未验证项。
  • 交付可检查的成果、验证结果和手测入口。

构建通过只证明构建成功。Agent 先核验受影响的关键路径，再请你验收产品体验；验证结论始终有适用范围，剩余风险需要明确说明。

03 / BATCH AGREEMENT开始前，约定这五件事

目标与范围
本批解决哪个用户问题，涉及哪些场景；优先级如何，做到哪里算完成。
可见成果
你最终能打开、操作或检查什么：页面、功能、文档或可运行版本，并给出可观察的成功标准。
不变量
哪些已有行为、数据、接口或架构边界必须保持。把兼容要求写成具体条件。
验证方式
Agent 如何证明关键行为成立，你如何手测效果。验证投入随风险选择，未覆盖项在交付时说明。
真正暂停条件
关键需求存在无法推断的分歧、需扩大授权范围、触及额度或权限边界、存在破坏性风险，或提交归属／合并冲突无法安全解决时，说明证据和所需决定。普通实现选择、范围内修复由 Agent 推进。

05 / HANDOFF一次集中交付，一次有重点的验收

交付时，Agent 应给出

  • 本批完成的成果与可打开的入口。
  • 关键路径的验证结果和必要证据。
  • 已知限制、未验证部分和相关阻塞。
  • 简短手测步骤与预期现象。
  • 按项目约定完成的提交、同步或产物状态。

手测时，你重点判断

  • 原始场景是否真正得到解决。
  • 关键操作是否自然、反馈是否清楚。
  • 约定必须保持的行为是否仍成立。
  • 阻塞与可后置优化是否分清。
  • 明确反馈“本批通过”或具体待修问题。

目标达到、必要检查完成后结束这一批。产品功能按项目交付规则提供体验产物；纯文档以内容、链接与必要静态检查验收。

06 / PROJECT MEMORY让经验进入下一次行动

项目把可复用的教训集中在工程经验索引中。经验生效靠每次任务实际读取、执行与更新。

  1. 开始时，按场景查经验Agent 查阅与本次任务相关的条目及正式文档，派工时带上相关经验、预期结果和失败停止条件。
  2. 执行时，让流程带着经验走一个项目 deepfield-delivery Skill 串起读取、派工、验证和收尾；AGENTS.md 提供必须遵守的约束。项目交付流程集中维护在这个 Skill 中。
  3. 完成时，把证实的教训留下对有复发价值的发现，优先补充或合并到原条目，并尽量落实为脚本检查或回归保护，让下次执行更可靠。

这些机制帮助减少重复失误，不能保证绝对不犯错。实际执行仍需证据、复核与必要验证；你发现偏差时，提供具体事实即可。
