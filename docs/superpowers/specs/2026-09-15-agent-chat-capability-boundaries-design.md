# Deepfield Agent、Chat 与 Capability 边界设计

日期：2026-09-15
状态：方向确认，增量落地

## 1. 目标

Deepfield 面向通用 Agent 产品演进，但不把 Chat、Capability 和工具揉成一个持续膨胀的执行器。本设计先明确长期边界，再用最小改动解决 Capability A 单公司调研无法稳定收口的问题。

当前版本不进行全面架构迁移。长期设计用于约束后续开发，当前里程碑只落地“统一、无工具、干净上下文的最终成稿阶段”。

## 2. 分层与职责

```text
产品层        Chat                         Capabilities
              对话、记忆、用户控制          固定流程、结果契约、产物管理
                         \                 /
执行层                    General Agent Runtime
                          模型调用、工具循环、预算、证据、收口
                                      |
工具层                    Search / Web / Files / Code / MCP
                          只提供能力，不决定何时及如何使用
```

### 2.1 通用 Agent Runtime

通用能力必须保持无产品状态、可组合、可观测：

- LLM Provider 与协议适配。
- 工具注册、调用、结果规范化及失败原因回传。
- 工具循环、轮次与额度控制。
- 本次运行的活动事件和诊断信息。
- 将工具结果整理为证据，而不是把工具协议当作最终答案。
- 关闭工具后的最终答案生成与输出校验。
- 取消、中断、超时和统一错误类型。

通用 Runtime 不拥有长期记忆，不决定是否联网，不知道“公司报告”或“聊天会话”的业务含义。

### 2.2 Chat 专属

- 对话及消息持久化。
- 多轮历史、长期记忆和后续可能的上下文压缩。
- 用户每轮的联网开关、停止与重新发送。
- 流式回答和永久化工具活动展示。
- 对话创建、切换、删除等交互。
- Chat 风格提示词和回答可读性规则。

Chat 负责决定本轮向 Runtime 开放哪些工具；Runtime 只执行该授权。

### 2.3 Capability 专属

- 明确的业务流程和阶段编排。
- 每阶段的输入、输出 Schema 和验证规则。
- 更紧的 Harness、预算、重试和失败分类。
- 结果落盘、版本和状态管理。
- 任务专属提示词，例如调研范围、截止日期、报告结构。
- 必要时读取上次产物和新的用户指令，但不继承隐式对话记忆。

Capability 是轻量、一次性的任务执行：运行上下文结束即释放，跨次运行只依赖显式输入与已保存产物。

### 2.4 工具与 Search Provider

- Provider 只负责把标准查询映射到外部服务并返回标准结果。
- Search 不管理 Agent 循环、搜索次数、访问网页策略或最终答案。
- 工具失败必须返回结构化错误，供 Runtime 和模型理解。
- 是否联网由产品层/Harness 决定，不由模型或 Search Provider 自行决定。

## 3. 关键运行契约

长期建议形成四个稳定对象：

- `AgentRunSpec`：模型、开放工具、预算、任务提示词、输出目标。
- `EvidenceBundle`：本次工具执行产生的正文、来源、失败与裁剪信息；不含模型工具协议消息。
- `FinalizationSpec`：最终答案目标、语言、格式、校验器及是否允许工具；默认不允许。
- `AgentRunResult`：最终文本、证据、活动、用量与错误。

产品层可持久化这些对象的不同部分：Chat 持久化消息与活动；Capability 持久化产物、阶段状态与必要证据；Runtime 本身不保存跨次状态。

## 4. 最终成稿必须是独立阶段

工具探索和最终成稿是两个不同动作：

1. 探索阶段允许调用工具，目标是收集足够证据。
2. 进入收口后工具永久关闭，不得重新打开。
3. 最终成稿只接收任务要求、必要的产品上下文和普通文本证据。
4. 最终请求不携带本轮 `toolCall` / `toolResult` 协议历史，也不携带“工具可用”的提示词。
5. 最终文本仍通过原有流式事件输出，并在产品层进行格式与协议泄漏校验。

这条边界既适用于 Chat，也适用于 Capability；两者只在任务提示词、保留的产品上下文和结果校验上不同。

## 5. 当前最小里程碑

本轮只完善一次调研，不做完整模块迁移：

- 在现有 `PiChatAgent` 内建立唯一的 `enterFinalization` 路径。
- “模型主动停止调用工具”和“达到轮次/工具额度”都进入同一路径。
- 进入收口时立即注入明确的用户级成稿指令。
- 收口上下文移除联网提示与所有工具协议消息，只保留任务、可用的普通对话上下文及文本证据。
- 最终调用显式禁用工具，且状态机禁止再次回到探索阶段。
- 保留现有流式输出、活动栏和最终文本校验。
- Capability A 继续使用既有报告结构化阶段，不在本轮重写。

## 6. 非目标

- 不在本轮抽出完整独立 npm 包或公共 SDK。
- 不新增向量记忆、模型路由或多 Agent 编排。
- 不重写 Search Provider。
- 不改变现有报告字段、页面结构或二轮结构化逻辑。
- 不以吞掉 DSML 字符串作为主要修复；协议泄漏仍应作为失败被检测。

## 7. 验收标准

- Capability A 即使消耗全部搜索/网页额度，也只进入一次最终成稿，并成功保存原始报告。
- 最终请求中无工具定义、无工具协议历史、无联网可用提示，且明确禁止工具。
- 最后一条工具失败或 `budget_trimmed` 会作为事实反馈给模型，但不会触发继续调用。
- 最终回答保持流式输出。
- Chat 的联网与非联网基本能力不回退；Chat 的历史/记忆仍归 Chat 管理。
- 工具活动、诊断和协议泄漏检测继续可用。

## 8. 后续演进顺序

1. 将本轮收口逻辑提取为通用 `AnswerFinalizer`。
2. 将工具结果整理提取为 `EvidenceBundle`。
3. 将 Chat 持久状态从 Runtime 构造参数中进一步剥离。
4. 为 Capability 建立统一的 workflow/step/output contract。
5. 新 Capability 只组合 Runtime 与工具，不复制 Chat 会话实现。
