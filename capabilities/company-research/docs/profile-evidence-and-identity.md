# 公司补全：来源编号与公司主体

公司补全仍在独立的 Pi 运行内完成，最多 3 次搜索、2 次网页读取。主题、展示名称、已有资料和用户主体提示共同限定检索方向，但只有本轮成功工具输出可以进入证据账本。

## 模型引用与落盘

账本按精确的 `kind + url` 分配本轮稳定的 `e1`、`e2` 等编号；重复获取同一来源沿用编号，同一 URL 的搜索摘要和已读网页分别编号。无内容、无效输出和失败工具不产生编号。每次成功工具输出携带仅含本次来源 `evidenceId/url/kind` 的目录。模型用 `{ "evidenceId": "e1" }` 引用，程序还原原始 URL 和类型，不修剪括号、不规范化 URL、不把摘要升级为已读网页。

宿主的可选 `toolOutputContext` 仅影响模型看到的 JSON：在原字段之前加 `capabilityContext` 字符串，保留单个合法 JSON 对象，以兼容 Pi 的检索进展与来源投影。原工具结果、审计、details 和成功输出的校验不变。没有回调、回调失败、超过 64,000 字符、原格式不支持或字段冲突时保持原结果。公司目录不含摘要正文；修正请求另带本轮原始来源及有界摘录。

模型引用支持编号，也兼容精确的 URL/kind 对象；来源仍须存在于本轮账本。引用失败与 JSON/Schema 失败共享最多一次无工具修正。修正只能使用既有证据、删除缺少依据的字段，不启动新的 Agent 或检索。第二次仍无效、取消、无搜索证据或模型接口失败就终止。诊断沿用 `formatRepair` 字段，以保持已有持久化兼容。

落盘继续使用原有 `identity/fields/fieldEvidence/sources` 和 URL/kind 结构，不存运行内编号，不修改旧资料，不需要迁移。

## 品牌、产品和公司

新的模型候选在 `matched` 身份上声明 `subjectType: company | brand | product`，并在 `reason` 中说明输入名称、研究主题与已核实主体之间的关系。公司匹配必须指向负责相关业务的公司；品牌/产品的上线日期、产品官网不能直接填写成公司成立日期、公司官网。不得混用集团、子公司、兄弟公司或历史主体资料。

仅匹配品牌或产品的候选会由程序转为 `unresolved`，字段清空，进入原有主体确认流程，不形成 ready 公司资料。缺少主体分类的匹配候选需通过同一次修正预算补正。已核实公司名称不等于法定全称；`legalName`、`headquarters` 等未知字段省略，至少保留一个有来源的有效字段即可。`subjectType` 只在模型边界使用，落盘仍由原有身份 disposition 表达是否完成公司核实。

用户展示名称与研究主题不被主体识别覆盖，业务关注也不能因此扩大到整个集团。该门禁核验引用归属和显式主体分类；证据是否在语义上支持主体及字段仍由模型依据公开来源判断，编号本身不代表事实正确。

## 失败呈现

来源核验失败映射为 `EXTERNAL.INVALID_RESPONSE`、`context.service = search`；格式失败为同一 code、`service = llm`；搜索或模型接口不可用继续使用 `EXTERNAL.UNAVAILABLE`。前端分别提示来源核验、结果格式、接口失败，不能把有搜索结果但引用错误显示成接口故障。

## 本地回归

定向覆盖带右括号的原始 URL、同 URL 不同来源类型、未知编号、缺失公司分类、品牌/产品降级、公司未知字段省略、一次共享修正预算、取消与无搜索证据，以及真实 Pi 工具循环仍执行 3 次搜索和 2 次读取。使用本地假 provider，不消耗真实 API。
